What contract accounts unlock on RISEx

Credit accounts, portfolio margin liquidation, order hooks, smart wallets and conditional orders, and the two changes they wait on

@degenRobot · mattsmart.xyz · November 2026 · Experiments on RISE testnet, not live products

A smart-contract account can already hold collateral on RISEx and validate signatures on chain. What it cannot do is trade under its own rules through RISEx's hosted API, or trade in the same transaction as its own logic without a role that has no published way to apply. RIP‑3 and RIP‑4 remove those two walls. This document shows what is on the other side.

Credit accounts

Needs RIP‑3 This experiment lends USDC.e to perps traders. Lenders deposit into one ERC-4626 pool. A borrower opens a credit account (a contract RISEx account owned by a credit manager contract), adds USDC.e or pledges WETH or WBTC, and draws USDC.e that lands as the account's RISEx margin.

An order that breaks the loan is an invalid signature

function isValidSignature(bytes32 hash, bytes calldata signature) public view returns (bytes4) {
    if (bytes4(signature[:4]) != ORDER_ENVELOPE_MAGIC) return 0xffffffff;
    OrderEnvelope memory e = abi.decode(signature[4:], (OrderEnvelope));

    // 1. Rebuild RISEx's digest from the order in the envelope. It must equal `hash`,
    //    so the envelope cannot approve any other message.
    if (_risexDigest(_witness(e)) != hash) return 0xffffffff;

    // 2. Who signed: the borrower, a liquidator or a keeper.
    SignerRole role = creditManager.signerRole(address(this), e.signer);
    if (role == SignerRole.None) return 0xffffffff;
    if (!SignatureCheckerLib.isValidSignatureNow(e.signer, hash, e.signature)) return 0xffffffff;

    // 3. Order policy, then the loan's health after the order. Reverts if either refuses.
    orderPolicy.checkPlaceOrder(address(this), role, uint88(e.data));
    return 0x1626ba7e;
}

The account's check, simplified to the place-order case. isValidSignature receives only a hash, and a contract cannot read an order out of a hash, so the signature carries the order itself. That is why it is 388 bytes long.

Health is the line (max(equity, 0) × equityRatio + Σ pledge × weight) / debt. Below 1, anyone may start a liquidation: the liquidator closes positions reduce-only, then the account withdraws the cash and pledge, repays the pool and pays a fee from the pledge.

Portfolio margin liquidation

Needs RIP‑4 A portfolio-margin account borrows against collateral held elsewhere and trades the loan on RISEx. RISE's own draft RIP‑2 describes one on Morpho, and says its liquidation closes perps and repays the loan "in a single atomic transaction" while each protocol keeps its own risk engine. Deposits and withdrawals on RISEx are open to any contract. Placing an order is not: on mainnet on 17 November 2026, PerpsManager.placeOrder was gated by role 14. Without the role the account closes through the hosted API in one transaction and repays in another, with the loan exposed in between.

function closeWithdrawRepay(MarketParams calldata loan, PlaceOrderParams calldata close)
    external onlyKeeper
{
    require(close.reduceOnly);
    perpsManager.placeOrder(close);   // trades for msg.sender, so this account needs role 14
    require(perpsManager.getPosition(close.marketId, address(this)).size == 0);

    uint256 amount = collateralManager.getWithdrawableUSDC(address(this)) / 1e12;
    collateralManager.withdraw(address(this), USDC, amount);
    morpho.repay(loan, amount, 0, address(this), "");
}

The test account's one extra function, simplified.

RISEx's risk engine is untouched for three reasons. The close is an ordinary reduce-only order from the account itself. RISEx's margin check and liquidator read the same account as before, and stay as the backstop if the product is late. And RISEx never prices the collateral: whether the WETH is worth enough is the lender's question on Morpho. One limit matters: the product's trigger has to sit ahead of RISEx's maintenance line, or RISEx liquidates first and the loan is left to its collateral. The credit account's liquidation above is the same pattern, already live on testnet.

Where a loss lands

All three designs give a trader more than RISEx alone would: more leverage, or a loan. In each, someone outside RISEx underwrites the extra, and RISEx's own margin check and liquidator run unchanged behind them.

Hooks

Needs RIP‑4 A hook gateway lets any RISEx account attach its own rules to its orders. For every order that can add risk, it runs in one transaction:

The account has no key of its own, so the only way to trade it is through its hooks. A hook is two functions; the risk-cap hook's pre-trade check is a few lines:

interface IOrderHook {
    function beforeOrder(OrderContext calldata ctx, bytes calldata hookData) external;
    function afterOrder(OrderContext calldata ctx, uint56 orderId, int256 sizeBefore,
                        int256 sizeAfter, bytes calldata hookData) external;
}

// RiskCapHook: refuse an order above the account's notional cap
function beforeOrder(OrderContext calldata ctx, bytes calldata) external view onlyGateway {
    uint256 cap = caps[ctx.account].maxOrderNotional;
    uint256 n = orderNotional(ctx);
    if (cap != 0 && n > cap) revert OrderTooLarge(n, cap);
}
HookWhat it enforcesWho wants it
Risk capOrder notional before; market leverage after the fillAnyone who wants a hard limit on their own account
Daily lossNo risk-adding orders past a daily loss limitProp firms and funded-account programmes
Delegate capAn operator's expiry, markets, per-order and cumulative capsOwners who let a manager, a friend or a bot trade

Live on testnet: an allowed order filled, an oversized order was refused on chain (OrderTooLarge), and a reduce-only close skipped the hooks. With RIP‑3, before-hooks could run inside an account's own isValidSignature through the API; after-hooks still need the gateway, because they act on the fill. One known limit: a resting order that fills later never comes back through the after-hooks.

Smart wallets

Needs RIP‑3 A passkey signs with the P-256 curve; the hosted API only recovers secp256k1 keys. So every passkey wallet must mint a second key just for RISEx, and that key carries none of the wallet's limits.

Orders anyone can relay

An account can approve an order by its content rather than by who sent it. The signature bytes carry the order; the account rebuilds the digest, checks the match, and tests the order against conditions its owner stored earlier. No owner key signs at submit time, so a keeper, a solver or the user's browser can submit it through the hosted API.

FeatureThe account accepts an order when
Stop‑loss, take‑profitIt is reduce-only and the oracle mark has crossed the owner's trigger
TWAP and DCAIt is the next slice of an approved schedule: size, interval, price limit
RebalancingIt moves exposure back toward the owner's target
Self-deleveragingIt is reduce-only and the account's health is below a threshold, so any keeper can protect it before RISEx's liquidator would

None of these needs a new order type from RISEx. The venue sees an ordinary order with a valid signature; the condition lives in the account. RISEx's liquidator still works on every account, because liquidation never asks for the account's signature.
